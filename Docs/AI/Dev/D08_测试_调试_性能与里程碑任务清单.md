## 3. ★ 双路径一致性测试（最重要）

### 3.1 目标

`Tier A/B` 走 GAS `UBrotatoDamageExecCalc`，`Tier C` 走纯函数 `FBrotatoDamagePipeline`。
两者**必须共享** `FBrotatoDamageMath`，因此结果必须逐位相同。任何分叉都意味着**有人在 ExecCalc 里偷偷写了公式**（违反 D00 §5.2 的 F7）。

### 3.2 实现

```cpp
// Tests/GAS/DualPathConsistencyTest.cpp
IMPLEMENT_SIMPLE_AUTOMATION_TEST(FDualPathTest,
    "Brotato.GAS.DualPathConsistency",
    EAutomationTestFlags::EditorContext | EAutomationTestFlags::ProductFilter)

bool FDualPathTest::RunTest(const FString&)
{
    const TArray<FDamageCase> Cases = GenerateCases();   // 见 §3.3
    for (int32 Seed = 0; Seed < 1000; ++Seed)
    {
        for (const FDamageCase& C : Cases)
        {
            FBrotatoRandom RngA; RngA.Seed(Seed);
            const FDamageResult A = RunThroughExecCalc(C, RngA);

            FBrotatoRandom RngB; RngB.Seed(Seed);
            const FDamageResult B = RunThroughPipeline(C, RngB);

            TestEqual(*FString::Printf(TEXT("[S%d][%s] Damage"),   Seed, *C.ToString()), A.Damage,    B.Damage);
            TestEqual(*FString::Printf(TEXT("[S%d][%s] Crit"),     Seed, *C.ToString()), A.bCrit,     B.bCrit);
            TestEqual(*FString::Printf(TEXT("[S%d][%s] Dodged"),   Seed, *C.ToString()), A.bDodged,   B.bDodged);
            TestEqual(*FString::Printf(TEXT("[S%d][%s] RngCalls"), Seed, *C.ToString()), A.RngCalls,  B.RngCalls);
        }
    }
    return true;
}
```

> ★ **`RngCalls` 必须一起断言**。只比对最终伤害会漏掉"某条路径多掷了一次骰"的 bug——单次看不出来，跑满 20 波后随机序列彻底错位。
> 注：此断言针对 **Combat 流内的同一次结算**（双路径对同一输入应有完全相同的取数次数），与"跨帧序列可复现"是两件事（§00 §5）。

### 3.3 用例生成矩阵（`GenerateCases()`）

| 维度 | 取值 |
|---|---|
| `Armor` | `-10, -1, 0, 1, 10, 20, 999` |
| `CritChance` | `0, 0.01, 0.5, 1.0` |
| `CritDamage` | `1.0, 1.5, 2.0, 3.0` |
| `Dodge` | `0, 0.3, 0.6, 0.9`（含超 cap） |
| `PercentDamage` | `-400, -100, 0, 30, 300` |
| `bBypassInvincibility` | `false, true` |
| `DamageType` | `Normal, Burning, Explosion, Contact` |
| `TargetTier` | `A(玩家), B(Boss), C(普通敌人)` |

笛卡尔积裁剪后约 **200 组** × 1000 seed = 20 万次断言，`-nullrhi` 下约 12 s。

## 6. ★ 黄金基线（回归快照）

> **前提（§00 §5.3）**：生产运行走**可变帧率**，黄金基线只在 **headless 固定步长**模式下跑，两者共用同一份代码路径：
> ```

>     -UseFixedTimeStep -FixedDeltaTime=0.0166667 -nullrhi -unattended -nop4
> ```
> `FApp::SetUseFixedTimeStep(true)` 是 UE 官方的确定性手段；**不为测试而在生产架构里塞固定帧循环**。

### 6.1 AI 自动局驱动器

`UBrotatoAutoPlaySubsystem`（**M2 就要搭好**）：

| 决策点 | 固定策略 |
|---|---|
| 移动 | 朝"远离最近敌人"的方向 |
| 升级 4 选 1 | 始终选第 1 个 |
| 商店购买 | 买得起就买第 1 格，否则不买 |
| 重掷 / 锁定 | 从不 |
| 武器选择 | 始终第 1 把 |

> 策略必须**完全确定**，不得读取墙钟时间、真实帧率、鼠标位置等非确定输入（`DeltaTime` 由 `-FixedDeltaTime` 固定）。

### 6.2 快照格式（每波一行）

```json
{
  "Wave": 7,
  "Gold": 143, "BonusGold": 5, "Level": 12, "Xp": 1580,
  "Stats": { "MaxHp": 34.0, "Damage": 12.0, "...16 主属性": 0.0 },
  "EnemiesKilled": 218, "MaterialsCollected": 176, "ConsumablesPicked": 3,
  "ActiveGECount": 31, "HookSlotEntryCount": 4,
  "WeaponRuntimeStatsHash": "a91c33f0",
  "RngCallCount": { "Shop": 312, "Loot": 1904, "Spawn": 688, "Combat": 45309 }
}
```

> ★ `RngCallCount` 按流分别记录（§00 §5.2）：
> - **Shop / Loot / Spawn** 三流零容差（离散事件，帧率无关 → 必须逐项相等）；
> - **Combat** 流只做**区间断言**（±1%），因为它与命中顺序相关；
> - 若 Shop/Loot/Spawn 先分叉，说明是**随机消耗次数**变了（例如某处漏了 `ChanceSuccess(0)` 的短路），而不是数值算错。

### 6.4 比较规则

| 字段类型 | 规则 |
|---|---|
| 整数 | **逐字节相等**，零容差 |
| 浮点 | 相对误差 `epsilon = 1e-4`（编译器优化会影响累加顺序） |
| 哈希字符串 | 完全相等 |
| 失败输出 | **首个分叉的「波次 + 字段名 + 期望值 + 实际值」** |

### 6.5 基线更新流程（★ 强约束）

1. CI 报告首个分叉的波次 + 字段
2. 判定：**bug** 还是 **有意变更**
3. 若 bug → 修代码，不动基线
4. 若有意变更 → 跑 `Brotato.Golden.Rebaseline`，**单独一个 commit**，PR 描述里写清"为什么允许变化"
5. ❌ **禁止**为了让 CI 变绿而无说明地更新基线
